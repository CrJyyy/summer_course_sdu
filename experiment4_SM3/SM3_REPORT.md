# SM3 软件实现与优化实验报告

> **课程**: SM3软件实现与优化 
> **内容**: 算法原理、x86/ARM64 架构优化详解、寄存器分配策略、实验结果与对比分析

---
## 摘要

本文基于 GM/T 0004-2012 SM3 密码杂凑算法标准，系统研究了 SM3 的软件实现与架构级优化方法。针对 x86-64 与 ARM64 两大主流平台，分别采用 AVX2/AVX512 与 NEON+GPR 混合策略，从消息加载、消息扩展、迭代压缩三个层面展开优化：利用 SIMD 指令完成大端序转换与 $W'$ 向量化生成，通过 64 轮全展开宏消除分支与字置换开销，并在 ARM64 上实现 On-the-fly 全寄存器操作。

**关键字**：SM3；密码杂凑算法；SIMD 优化；AVX2；AVX512；ARM64；NEON；性能优化；循环展开

---
##  算法原理与优化思路

### 1. SM3 核心流程

SM3 对消息按 **512-bit 分组** 进行处理，每组包含：

1. **消息扩展**：由 16 字消息生成 68 字 `W[0..67]` 和 64 字 `W′[0..63]`。
   - `Wj = P1(Wj-16 ⊕ Wj-9 ⊕ ROTL32(Wj-3,15)) ⊕ ROTL32(Wj-13,7) ⊕ Wj-6`  (j = 16..67)
   - `W′j = Wj ⊕ Wj+4`  (j = 0..63)
2. **迭代压缩（CF）**：64 轮更新 8 个 32-bit 状态字 `A..H`。
3. **杂凑值更新**：`V(i+1) = V(i) ⊕ CF(V(i), B(i))`。

### 2. 基本优化思路

1. **代码扁平化**：将循环展开为顺序执行的宏调用，消除分支预测失败与循环控制开销。
2. **减少数据依赖性**：`W′j = Wj ⊕ Wj+4` 之间无数据依赖，适合 SIMD 并行计算。
3. **SIMD-GPR 分离**：
   - SIMD 负责：消息加载、大端→小端转换、`W′` 批量异或（位运算吞吐高）。
   - GPR 负责：64 轮压缩（存在 `A→B→C→D` 的严格依赖链，标量寄存器更灵活）。
4. **避免内存写**：X86 架构下尽量减少对栈的写回；中间变量优先驻留寄存器。
5. **On-the-fly（在线扩展）**：不预存全部 `W[68]`，而是边扩展边压缩，减少缓存占用与内存带宽压力。

### 3. 标量实现的核心瓶颈分析

在标量常规实现中，SM3 存在三个严重的计算瓶颈，直接制约了在现代超标量处理器上的性能表现：

**（1）大端序逆序开销**

SM3 密文规范输入为大端序，而主流 PC/手机处理器皆为小端序。标量版每个消息分组（64 字节）需进行 16 次手动字反转（SWAP32），频繁使用移位和掩码操作，消耗大量指令发射带宽。

**（2）数据依赖阻碍流水线**

消息扩展递推公式 $W_j = P_1(W_{j-16} \\oplus W_{j-9} \\oplus \\text{ROTL32}(W_{j-3}, 15)) \\oplus \\text{ROTL32}(W_{j-13}, 7) \\oplus W_{j-6}$ 存在严重跨步数据回溯依赖（如依赖 $W_{j-16}$、$W_{j-9}$、$W_{j-3}$ 等），限制了超标量 CPU 乱序执行（OoO）的并行度。

**（3）字置换开销**

压缩轮函数中包含 `A→B→C→D` 与 `E→F→G→H`的密集更新移位。如果采用物理寄存器逐轮拷贝（`D=C; C=ROTL(B,9)...`），会向发射队列塞满无意义的 `mov` 指令，极度消耗处理器指令发射带宽。

## x86-64 架构优化实现

### 1. AVX2/AVX512 宽位加载与字节序转换

SM3 输入消息为大端序，x86 为小端序。传统方法需逐字节移位拼接，本项目使用 **shuffle 指令** 一次完成 32B（AVX2）或 64B（AVX512）的转换：

**AVX2 路径**：使用一个 256 位静态只读洗牌掩码，配合 `_mm256_shuffle_epi8`，在 2 个时钟周期内完成 64 字节数据大端字节反转：

```c
// AVX2: 32 字节对齐的 shuffle mask
static const uint8_t SM3_SHUF_AVX2[32] alignas(32) = {
    3,2,1,0, 7,6,5,4, 11,10,9,8, 15,14,13,12,
    3,2,1,0, 7,6,5,4, 11,10,9,8, 15,14,13,12
};
__m256i shuf = _mm256_load_si256((const __m256i *)SM3_SHUF_AVX2);
__m256i v0 = _mm256_shuffle_epi8(_mm256_loadu_si256((const __m256i *)block), shuf);
__m256i v1 = _mm256_shuffle_epi8(_mm256_loadu_si256((const __m256i *)(block + 32)), shuf);
_mm256_store_si256((__m256i *)&W[0], v0);
_mm256_store_si256((__m256i *)&W[8], v1);
```

**AVX512 路径**：采用 512 位单指令大宽加载 `_mm512_loadu_si512`，在单一周期内通道化并行逆序：仅需 **1 条 `vpshufb`** 即可处理整个 64B 消息块

```c
__m512i shuf = _mm512_load_si512((const __m512i *)SM3_SHUF_AVX512);
__m512i v = _mm512_shuffle_epi8(_mm512_loadu_si512((const __m512i *)block), shuf);
_mm512_store_si512((__m512i *)&W[0], v);
```

### 2.  向量化 W′ 生成

`W′j = Wj ⊕ Wj+4` 各组之间完全独立，天然适合 SIMD：

- **AVX2**：256-bit / 32-bit = **8 words/次**，循环 8 次完成 64 字。
- **AVX512**：512-bit / 32-bit = **16 words/次**，循环 4 次完成 64 字。

对比标量版本的 64 次异或指令，AVX2 减少为 8 次，AVX512 减少为 4 次。

### 3. GPR 64 轮全展开压缩

采用 **无参数交换** 的宏设计，直接操作外部变量 `A..H`，确保语义正确且编译器可将所有状态变量分配至 16 个通用寄存器中：

```c
#define SM3_ROUND(j, TJ, FF, GG) do {     uint32_t _ss1 = ROTL32(ROTL32(A, 12) + E + ROTL32((uint32_t)(TJ), (j)), 7);     uint32_t _ss2 = _ss1 ^ ROTL32(A, 12);     uint32_t _tt1 = FF(A, B, C) + D + _ss2 + Wp[j];     uint32_t _tt2 = GG(E, F, G) + H + _ss1 + W[j];     D = C;  C = ROTL32(B, 9);  B = A;  A = _tt1;     H = G;  G = ROTL32(F, 19);  F = E;  E = P0(_tt2); } while(0)
```

64 轮直接顺序调用 `SM3_ROUND(0..63)`，消除：
- 循环变量 `j` 的递增与比较；
- 每轮结束时的显式 `tmp=A; A=B; ...` 字置换；
- 函数调用开销（宏内联）。

### 4. 运行时指令集分发

当编译器在 MSVC 模式下，允许在没有命令行特定选项的情况下编译高阶 intrinsic 函数；GCC/Clang 下通过条件编译宏保护 AVX2/AVX512 代码路径

通过 `cpuid` 与 `xgetbv` 检测 AVX512BW / AVX2 / SSE 支持情况，函数指针 `g_compress_fn` 在首次调用时自动绑定最优路径，保证二进制兼容性：

```c
if (cpu_has_avx512_bw())      g_compress_fn = sm3_compress_avx512;
else if (cpu_has_avx2())      g_compress_fn = sm3_compress_avx2;
else                          g_compress_fn = sm3_compress_scalar;
```

### 5. 内存操作数的利用（x86 Skylake 优化）

PPT 指出，Skylake 架构支持 `add reg, mem`（端口 p23），吞吐为 0.5 cycle。因此压缩宏中 `Wp[j]` 与 `W[j]` 直接以内存操作数形式参与加法：

```c
uint32_t _tt1 = FF(A, B, C) + D + _ss2 + Wp[j];  // Wp[j] 来自栈/缓存
```

编译器可生成 `add eax, [rsp+0x40]` 形式的指令，避免先 `mov` 到寄存器再 `add`，节省指令数与寄存器占用。

## ARM64 架构优化实现

### 1. NEON 向量加载与大端转换

利用 NEON 128 位向量单元将整个 64 字节分组一次性装载至 4 个寄存器中。运用 ARM64 的 `rev32` 指令（对应 NEON `vrev32q_u8`）进行全通道并行字节逆序:

```c
uint32x4_t w0 = vreinterpretq_u32_u8(vrev32q_u8(vld1q_u8(block)));
uint32x4_t w1 = vreinterpretq_u32_u8(vrev32q_u8(vld1q_u8(block + 16)));
uint32x4_t w2 = vreinterpretq_u32_u8(vrev32q_u8(vld1q_u8(block + 32)));
uint32x4_t w3 = vreinterpretq_u32_u8(vrev32q_u8(vld1q_u8(block + 48)));
vst1q_u32(&r[0], w0);
vst1q_u32(&r[4], w1);
vst1q_u32(&r[8], w2);
vst1q_u32(&r[12], w3);
```

4 条 NEON 指令完成 64 字节加载 + 字节序转换，之后 `r[0..15]` 存放小端序的 `W0..W15`。
该操作消除了串行标量移位拼装的大量指令。

### 2. On-the-fly 消息扩展与迭代压缩交错

为了最大化指令并行度,不预计算全部 `W[68]`，而是在 64 轮压缩宏内部，利用 16 字节对齐的环形缓冲区 `r[16]` 实时生成所需 `Wj`,编译器自动将其提升至通用寄存器，完全消除栈交互和内存回写开销：

```c
uint32_t wj = r[(j) % 16];
if ((j) >= 12) {
    r[((j) + 4) % 16] = P1(r[((j) + 4) % 16] ^ r[((j) + 11) % 16] ^ 
                           ROTL32(r[((j) + 1) % 16], 15)) ^ 
                           ROTL32(r[((j) + 7) % 16], 7) ^ r[((j) + 14) % 16];
}
uint32_t wj_prime = wj ^ r[((j) + 4) % 16];
```

- 当 `j < 12` 时，直接读取 `r[j]` 与 `r[j+4]` 作为 `Wj` 与 `Wj+4`。
- 当 `j >= 12` 时，先递推生成新的字写入 `r[(j+4)%16]`，再计算 `W′j`。
- 仅需 16 字缓冲区，大幅减少对栈的写操作。

### 3. 消除字置换的循环展开

SM3 每轮压缩后需进行字置换：

```
A→B, B→C, C→D, TT1→A
E→F, F→G, G→H, P0(TT2)→E
```

传统实现每轮需 6~7 条 `mov` 指令,本项目采用课程 PPT 所述的 **4 轮组合宏参数交换** 技巧,通过编译时静态轮换逻辑寄存器指针来实现全展开。每组 4 轮为一个完整循环：

```c
ROUND_0_15(A, B, C, D, E, F, G, H, 0);
ROUND_0_15(D, A, B, C, H, E, F, G, 1);
ROUND_0_15(C, D, A, B, G, H, E, F, 2);
ROUND_0_15(B, C, D, A, F, G, H, E, 3);
```

宏内部仅更新 `D=TT1`、`B=ROTL(B,9)`、`H=P0(TT2)`、`F=ROTL(F,19)`，其余变量保持原位。通过改变下一轮宏调用的参数顺序，**逻辑上完成了字置换，物理上消除了显式的寄存器移动指令**。4 轮为一个周期，第 4 轮后变量名与物理寄存器重新对齐。这一机制消除了轮次之间 75% 的寄存器移动（MOV）操作。

### 4. 桶形移位寄存器（Barrel Shifter）深度融合

ARM64 支持在逻辑运算单周期内执行免费移位。在计算 $SS1$ 和 $SS2$ 时，`ROTL32` 和累加合并在单个时钟周期内发射（即 `eor` 移位组合），相比传统 x86 指令数减少近 30%。ARM64 拥有 30 个可用 GPR（`w0..w17, w19..w30`），16 字滑动窗口 + 8 状态字 + 中间变量可完全驻留寄存器，实现**全寄存器操作**。

## 深入分析

### 1. 为什么 W[16..67] 的递推难以 SIMD 化？

SM3 消息扩展递推公式：

```
Wj = P1(Wj-16 ⊕ Wj-9 ⊕ ROTL32(Wj-3, 15)) ⊕ ROTL32(Wj-13, 7) ⊕ Wj-6
```

该递推存在 **3-step 数据依赖**（`Wj` 依赖 `Wj-3`），导致无法像 `W′` 那样直接用 8-wide 或 16-wide SIMD 并行计算。PPT 中指出，若强行用 SIMD 实现，需要大量 `vpalignr` 拼接与 `vpshufd` 重排，单路场景下反而因端口竞争（shuffle 端口通常为 p5）而收益有限。

因此，**务实策略**是：
- **保留标量递推**计算 `W[16..67]`（仅需 52 轮，且可提前与压缩交错）。
- **SIMD 加速无依赖的 `W′` 生成**与**初始消息加载**。

### 2. x86 AVX2 的 W′ 向量化

`W′j = Wj ⊕ Wj+4` (j = 0..63) 可视为 64 个独立的 32-bit 异或。AVX2 的 `vpxor` 在 256-bit 寄存器上可同时处理 8 个 32-bit 字：

```c
for (int j = 0; j < 64; j += 8) {
    __m256i a = _mm256_loadu_si256((__m256i *)&W[j]);
    __m256i b = _mm256_loadu_si256((__m256i *)&W[j + 4]);
    _mm256_storeu_si256((__m256i *)&Wp[j], _mm256_xor_si256(a, b));
}
```

循环仅执行 8 次，每次 1 条 `vpxor`（吞吐 0.33 cycle，端口 p015），整个 `W′` 生成阶段仅需约 **2.7 cycles**。



### 3. 寄存器分配策略

#### x86-64（16 个 GPR）

| 用途 | 寄存器数量 | 说明 |
|------|-----------|------|
| 状态字 A..H | 8 | 全程驻留 |
| 中间变量（ss1, ss2, tt1, tt2） | 4 | 轮内临时计算 |
| 基址/索引 | 2 | `block` 指针、循环计数（若未全展开） |
| 剩余 | 2 | 留给编译器调度，避免溢出 |

在 64 轮全展开 + `-O3` 下，编译器可将 `W[0..67]` 与 `Wp[0..63]` 的活跃部分缓存到寄存器，或利用 L1 D-Cache 的低延迟（4 cycles）直接内存操作数访问。

#### ARM64（30 个可用 GPR）

| 用途 | 寄存器数量 | 说明 |
|------|-----------|------|
| 状态字 A..H | 8 | 全程驻留 |
| 16 字滑动窗口 r[0..15] | 16 | 编译器提升为 GPR |
| 中间变量 / Tj | 4~6 | 轮内计算 |
| 剩余 | >2 | 充裕，可存放更多常量 |

ARM64 的寄存器充裕性使得 **全寄存器实现** 成为可能,，这也是 NEON+GPR 混合实现性能亮眼的关键。

## 实验结果与对比

> **测试方法**：处理 100 MB（10 MB × 10 次迭代），取平均吞吐量。

### 3. 结果分析

1. x86-64 AVX2 ：
   - 消息加载：从 16 次 32-bit 移位拼接 → 2 次 256-bit `vpshufb`，加载阶段指令数减少约 **87%**。
   - `W′` 生成：从 64 次标量 `xor` → 8 次 256-bit `vpxor`，指令数减少 **87.5%**。
   - 压缩阶段：64 轮全展开消除循环分支，配合 `-O3` 编译器可将 `A..H` 与 `W′` 缓存到 16 个 GPR 中，减少内存读写。

2. x86-64 AVX512 ：
   - 单条 `vpshufb` 完成 64B 消息块字节序转换，加载阶段进一步减半。
   - `W′` 仅需 4 次 512-bit 异或，理论上比 AVX2 再减少 50% 指令。
   - 实测提升受限于：单路 SM3 的压缩阶段仍是 GPR 标量执行，整体加速比遵循 **Amdahl 定律**。

3. ARM64 NEON ：
   - `vrev32q_u8` 完美匹配 SM3 大端转小端需求，4 条指令完成 64B 转换。
   - On-the-fly 策略将 `W` 存储从 68 字压缩到 16 字滑动窗口，显著降低栈内存流量。
   - ARM64 拥有 30 个可用 GPR，全展开后所有中间变量可驻留寄存器，避免 X86 上常见的“寄存器溢出到栈”问题。

## 6. 已知问题与注意事项

1. **虚拟机 AVX 检测失败**：若运行 x86 版本时始终回退到 `Scalar path`，请检查：
   - 宿主机 CPU 是否支持 AVX2/AVX512；
   - 虚拟机设置是否启用了“向客户机公开硬件辅助的 CPU 虚拟化”（如 VMware 的 `vhv.enable = TRUE`）；
   - 容器/云服务器是否通过 `cpuid` 屏蔽了 AVX 标志位。

2. **代码体积**：64 轮全展开会显著增大 `.text` 段，嵌入式场景（Cortex-M3/M4）需谨慎使用，建议仅在高性能服务器/移动平台启用。
